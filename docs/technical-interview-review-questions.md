# Technical interview review questions

This is a source-grounded discussion guide, not a scripted account of personal work. Links point to the audited commits listed in the [technical evidence guide](technical-interview-evidence.md). The answer describes what the public code and tests support; each boundary states what they do **not** prove.

1. **Why keep ISR work bounded?** An interrupt should acknowledge the event and transfer a small, bounded item so later bytes are not delayed by parsing or formatting. In [STC8 UART1 ISR](https://github.com/REliasCheng/STC8-MCU-Learning/blob/c517009a25e3560074f76a20274dc04956c1cdf2/platform/stc8/stc8_uart_sdcc.c), SBUF/RI handling feeds the receive path; [foreground frame drain](https://github.com/REliasCheng/STC8-MCU-Learning/blob/c517009a25e3560074f76a20274dc04956c1cdf2/src/core/uart_frame_drain.c) handles complete frames, with [Host tests](https://github.com/REliasCheng/STC8-MCU-Learning/blob/c517009a25e3560074f76a20274dc04956c1cdf2/tests/test_uart_frame.c). **Boundary:** target linkage/vector checks do not measure ISR latency, stack high-water mark or board UART behavior.

2. **What happens when a ring buffer fills?** The policy must be explicit: latch overflow, reject the damaged frame and resynchronize at a known delimiter rather than execute a truncated command. The [command engine](https://github.com/REliasCheng/Embedded-C-Cpp-Learning/blob/a80a44950bdeb525dbad2b7eb3bc22d8012f5d7f/projects/06_%E7%BB%BC%E5%90%88%E8%BD%AF%E4%BB%B6%E5%AE%9E%E8%B7%B5/%E5%B5%8C%E5%85%A5%E5%BC%8F%E5%91%BD%E4%BB%A4%E5%A4%84%E7%90%86%E6%A1%86%E6%9E%B6/practice/src/command.c) and [overflow recovery test](https://github.com/REliasCheng/Embedded-C-Cpp-Learning/blob/a80a44950bdeb525dbad2b7eb3bc22d8012f5d7f/projects/06_%E7%BB%BC%E5%90%88%E8%BD%AF%E4%BB%B6%E5%AE%9E%E8%B7%B5/%E5%B5%8C%E5%85%A5%E5%BC%8F%E5%91%BD%E4%BB%A4%E5%A4%84%E7%90%86%E6%A1%86%E6%9E%B6/tests/test_command_framework.c) use LF to recover. **Boundary:** Host input tests do not establish actual interrupt arrival rates.

3. **Why does a send timeout not always mean the byte failed?** A timeout can mean the completion signal was not observed within the polling budget after SBUF was written. Blind retry can duplicate output. [BlueBridge UART policy](https://github.com/REliasCheng/BlueBridgeCup-MCU/blob/92949b881c148efb8bf1dc4060e9a1ab65f65ff3/practice/peripheral-driver-corrections/uart_safe.c) returns a distinct timeout and retains busy state; [tests](https://github.com/REliasCheng/BlueBridgeCup-MCU/blob/92949b881c148efb8bf1dc4060e9a1ab65f65ff3/practice/peripheral-driver-corrections/tests/test_uart_safe.c) check timeout/busy/recovery. **Boundary:** this policy has Host shim tests; no actual UART waveform or wire-level delivery was measured.

4. **Why use an OTA Journal?** It records phase transitions across interrupted copy operations so recovery can distinguish a verified Staging image from an applied Active image. [Journal write/recovery](https://github.com/REliasCheng/Embedded-OTA-Update-Lab/blob/0cec602fa2c1f890eb7ea8e2e98e759e5762ef6a/src/ota_update.c) and [fault tests](https://github.com/REliasCheng/Embedded-OTA-Update-Lab/blob/0cec602fa2c1f890eb7ea8e2e98e759e5762ef6a/tests/test_ota_update.c) cover corrupt records and explicit retry. **Boundary:** memory Flash simulation does not prove power-loss atomicity, bootability, authentication or an MCU-specific erase/program contract.

5. **What can the FreeRTOS Host Port prove?** It exercises the real pinned Kernel's Queue, tasks, notifications and Mutex with repository application logic. [Task pipeline](https://github.com/REliasCheng/FreeRTOS-Embedded-Lab/blob/e65cec6eb5f02fd6e9e8dd2cbf416ea4586d0510/app/rtos_demo.c) and [application tests](https://github.com/REliasCheng/FreeRTOS-Embedded-Lab/blob/e65cec6eb5f02fd6e9e8dd2cbf416ea4586d0510/tests/test_processing.c) cover normal/backpressure/timeout paths. **Boundary:** a POSIX Host Port cannot establish Cortex-M scheduling latency or safe `FromISR` behavior.

6. **How does LVGL headless testing differ from a real LCD?** The same LVGL UI can process events and flush pixels to a checked memory buffer; it tests widget and frame behavior without an electrical display. [UI](https://github.com/REliasCheng/LVGL-Embedded-GUI-Lab/blob/1bc8ab0af33b78ebc00264df885913b39802cb6d/app/dashboard_ui.c) and [headless renderer test](https://github.com/REliasCheng/LVGL-Embedded-GUI-Lab/blob/1bc8ab0af33b78ebc00264df885913b39802cb6d/tests/dashboard_headless.c) cover screen/pointer/pixel changes. **Boundary:** LCD, touch, DMA, cache and target task timing are untested.

7. **Why must QoS 1 consumers handle duplicates?** MQTT QoS 1 permits redelivery; an idempotent command should recognize a repeated request ID/value and avoid applying the switch change twice. The [device model](https://github.com/REliasCheng/Wireless-IoT-Embedded-Lab/blob/b71ff86e4e9fed0fdaae6d133904c802aa80ccf3/app/device_model.c) and [Broker integration scenarios](https://github.com/REliasCheng/Wireless-IoT-Embedded-Lab/blob/b71ff86e4e9fed0fdaae6d133904c802aa80ccf3/tests/mqtt_integration.py) exercise deduplication/reconnect. **Boundary:** the state is in memory, with no process-restart persistence, cloud or radio proof.

8. **What does a PTY test prove beyond a byte-array mock?** It exercises real Linux file descriptors, `termios`, partial I/O and `poll` against a Host kernel PTY, while retaining a controlled peer. See [device port](https://github.com/REliasCheng/ARM-Linux-Embedded-Lab/blob/682246f2cbee1342cfc668ab027630ef18fd52e3/src/linux_device_port.c) and [PTY scenarios](https://github.com/REliasCheng/ARM-Linux-Embedded-Lab/blob/682246f2cbee1342cfc668ab027630ef18fd52e3/tests/pty_integration.py). **Boundary:** the PTY does not model a specific RK3566 UART driver, wiring or permissions at deployment.

9. **What do AArch64 cross-build and QEMU user mode each show?** Cross compilation creates an AArch64 Linux ELF; QEMU user mode executes that userspace binary and tests software behavior on an emulated instruction set. The [toolchain/QEMU guide](https://github.com/REliasCheng/ARM-Linux-Embedded-Lab/blob/682246f2cbee1342cfc668ab027630ef18fd52e3/docs/aarch64-build-verification.md) and [CI workflow](https://github.com/REliasCheng/ARM-Linux-Embedded-Lab/blob/682246f2cbee1342cfc668ab027630ef18fd52e3/.github/workflows/linux-device.yml) give commands and run steps. **Boundary:** neither boots a kernel or proves board Device Tree, module load or hardware access.

10. **Why is generic C52 simulation not STC board validation?** It executes linked MCS-51 instructions and can inspect software state, but cannot substitute for STC-specific SFR behavior or external circuits. [STC89 target entry](https://github.com/REliasCheng/stc89c52-learning/blob/e1350c5d253ab1e786ba9f18f2e442f183a84c1b/target/sdcc/main.c), [build/simulation guide](https://github.com/REliasCheng/stc89c52-learning/blob/e1350c5d253ab1e786ba9f18f2e442f183a84c1b/docs/sdcc-target-build.md) and [core tests](https://github.com/REliasCheng/stc89c52-learning/blob/e1350c5d253ab1e786ba9f18f2e442f183a84c1b/projects/13_%E7%8E%AF%E5%A2%83%E4%B8%8E%E6%97%B6%E9%92%9F%E4%BF%A1%E6%81%AF%E7%BB%88%E7%AB%AF/practice/tests/test_terminal_app.c) show the tier. **Boundary:** RTC, temperature, OLED, EEPROM and board timing remain unverified; BlueBridge's C52 policy run likewise does not validate CT107D latches.

11. **How do CODE/DATA/IDATA/XDATA budgets affect MCU design?** They constrain placement, stack and interface choices; a linker map reports allocation but not peak runtime stack. [STC8 build guide](https://github.com/REliasCheng/STC8-MCU-Learning/blob/c517009a25e3560074f76a20274dc04956c1cdf2/docs/sdcc-target-build.md) records CODE/XDATA/vector checks, while [BlueBridge target guide](https://github.com/REliasCheng/BlueBridgeCup-MCU/blob/92949b881c148efb8bf1dc4060e9a1ab65f65ff3/docs/sdcc-target-build.md) reserves IAP15 debugger-related ranges; [target source](https://github.com/REliasCheng/BlueBridgeCup-MCU/blob/92949b881c148efb8bf1dc4060e9a1ab65f65ff3/target/sdcc/main.c) uses a constrained diagnostic path. **Boundary:** map fit and simulator state are not stack high-water, chip-debugger startup or board-load proof.

12. **Why is a Robotics Fault Latch not a physical E-stop?** A software latch refuses further Fake Bus commands until explicit recovery, making error paths testable. [Offline controller](https://github.com/REliasCheng/Embodied-Robotics-Arm-Lab/blob/b21e2f47bf82f3fbe623fa2343a8ac768a716173/offline_control/controller.py) and [fault/replay tests](https://github.com/REliasCheng/Embodied-Robotics-Arm-Lab/blob/b21e2f47bf82f3fbe623fa2343a8ac768a716173/tests_offline/test_control.py) provide the example. **Boundary:** neither a physical stop circuit nor a real motor bus, calibration or mechanical safety has been tested.
