# Technical interview evidence

## Engineering capabilities demonstrated by public source and CI

This is a reading route for embedded software, firmware, MCU, Host tooling and IoT/Linux interviews. It describes **observable repository implementations**, not employment history or a claim of expertise across every named platform. The eight projects below demonstrate bounded C/C++ and Python modules, state and failure handling, ISR/front-end separation, SDCC target compilation, real FreeRTOS Kernel execution on a Host Port, LVGL rendering, loopback MQTT integration, Linux PTY I/O and AArch64 userspace cross-build/QEMU execution. Each claim is tied to a source file, test and successful CI run. The [14-repository matrix](engineering-evidence-quality-review.md) supplies the full inventory.

All links below refer to **specific audited commits** (2026-10-27 or 2026-10-28). These runs are historical success for their `head_sha`, not perpetual status for future `main` commits. Reproduction commands were **reviewed against source and workflow**; they were not rerun for all eight projects during this documentation review (`REPRODUCTION_COMMAND_REVIEWED`). Commands run by linked CI are identified separately. No physical board, sensor, radio, motor or flash operation is claimed. Repository root licenses do not relicense upstream dependencies or historical course/vendor content.

## 1. Python Host Application — testable serial application

- **Project / evidence:** [repository](https://github.com/REliasCheng/Python-Host-Application-Lab) at `13a1ffb81bb0d4b9ee72c819750b08e99c2f52ef`; [application coordinator](https://github.com/REliasCheng/Python-Host-Application-Lab/blob/13a1ffb81bb0d4b9ee72c819750b08e99c2f52ef/src/host_app/core/application.py), [GUI tests](https://github.com/REliasCheng/Python-Host-Application-Lab/blob/13a1ffb81bb0d4b9ee72c819750b08e99c2f52ef/tests/test_gui.py), [main CI](https://github.com/REliasCheng/Python-Host-Application-Lab/actions/runs/40161227325), [architecture](https://github.com/REliasCheng/Python-Host-Application-Lab/blob/13a1ffb81bb0d4b9ee72c819750b08e99c2f52ef/docs/system-architecture.md).
- **Problem / implementation / architecture:** Make a line-oriented serial tool testable without a connected device. The repository's `HostApplication` coordinates connection state, command encoding, incremental receive parsing and a pluggable `SerialBackend`; PyQt5 is a separately installed UI dependency and pyserial is an optional real-port adapter. Data flows GUI → coordinator → protocol/state → backend.
- **Technical challenge / failure handling:** Partial writes are rejected; a close exception leaves the UI recoverable when the port remains open. Completed receive lines are retained even when later bytes in the same read trigger a protocol error. Tests exercise close failure, reconnect, write retry and mock GUI paths.
- **Verification / limitations:** The commit-bound CI runs Python tests, quality checks, package build and offscreen Qt GUI with an in-memory backend. It does **not** establish communication with a physical device or a real serial driver under failure.
- **Reproduce:** On Python 3.10–3.12 with the declared test/GUI dependencies, from the repository root run `python -m pip install -e ".[gui,serial,test]"` then `python -m pytest -o addopts='' tests/test_gui.py` (`QT_QPA_PLATFORM=offscreen` on a headless Linux host). This checks Host GUI/mock behavior; no peripheral is required. The exact matrix and wheel smoke are in the linked workflow.
- **Discussion points:** How should a GUI behave if closing a port raises while it is still open? How should a parser surface completed messages before reporting a later malformed frame?

## 2. Embedded C/C++ Core — bounded command processing

- **Project / evidence:** [repository](https://github.com/REliasCheng/Embedded-C-Cpp-Learning) at `a80a44950bdeb525dbad2b7eb3bc22d8012f5d7f`; [command engine](https://github.com/REliasCheng/Embedded-C-Cpp-Learning/blob/a80a44950bdeb525dbad2b7eb3bc22d8012f5d7f/projects/06_%E7%BB%BC%E5%90%88%E8%BD%AF%E4%BB%B6%E5%AE%9E%E8%B7%B5/%E5%B5%8C%E5%85%A5%E5%BC%8F%E5%91%BD%E4%BB%A4%E5%A4%84%E7%90%86%E6%A1%86%E6%9E%B6/practice/src/command.c), [tests](https://github.com/REliasCheng/Embedded-C-Cpp-Learning/blob/a80a44950bdeb525dbad2b7eb3bc22d8012f5d7f/projects/06_%E7%BB%BC%E5%90%88%E8%BD%AF%E4%BB%B6%E5%AE%9E%E8%B7%B5/%E5%B5%8C%E5%85%A5%E5%BC%8F%E5%91%BD%E4%BB%A4%E5%A4%84%E7%90%86%E6%A1%86%E6%9E%B6/tests/test_command_framework.c), [main CI](https://github.com/REliasCheng/Embedded-C-Cpp-Learning/actions/runs/39929657668).
- **Problem / implementation / architecture:** Accept a bounded byte stream and change device model state only after a complete, valid command. The repository implementation separates ring-buffer ingress from foreground tokenization, handler dispatch and reply formatting; the lightweight task table is another portable single-threaded module, not an RTOS.
- **Technical challenge / failure handling:** A response buffer that is too small must leave state unchanged. Input overflow discards the damaged frame through LF, and embedded NUL or inline CR rejects the whole frame; tests target those recovery paths. The feed API is a software ingress boundary, not proof that an actual ISR is safe or connected.
- **Verification / limitations:** GCC, Clang and sanitizer Host tests passed at the linked SHA. No MCU cross-build, UART waveform, interrupt latency or board runtime is established.
- **Reproduce:** With Python 3 and GCC on Windows/Linux, run `python scripts/run_host_tests.py --compiler gcc` from the repository root; change to `clang` where installed. This compiles and executes five portable Host test groups, without hardware or proprietary tooling.
- **Discussion points:** Why commit a state mutation only after the reply fits? What resynchronization rule prevents an overflowing frame from executing as a truncated command?

## 3. Embedded OTA — journaled Host update model

- **Project / evidence:** [repository](https://github.com/REliasCheng/Embedded-OTA-Update-Lab) at `0cec602fa2c1f890eb7ea8e2e98e759e5762ef6a`; [update engine](https://github.com/REliasCheng/Embedded-OTA-Update-Lab/blob/0cec602fa2c1f890eb7ea8e2e98e759e5762ef6a/src/ota_update.c), [tests](https://github.com/REliasCheng/Embedded-OTA-Update-Lab/blob/0cec602fa2c1f890eb7ea8e2e98e759e5762ef6a/tests/test_ota_update.c), [main CI](https://github.com/REliasCheng/Embedded-OTA-Update-Lab/actions/runs/40311425747), [reproduction guide](https://github.com/REliasCheng/Embedded-OTA-Update-Lab/blob/0cec602fa2c1f890eb7ea8e2e98e759e5762ef6a/docs/host-update-flow.md).
- **Problem / implementation / architecture:** Model an update path that can reject corrupt blocks and identify interrupted apply operations. Original portable C11 code composes block/manifest CRC, a Flash port, an injectable memory simulator and a two-slot Journal. Flow: receive into Staging → whole-image reread/CRC → READY → copy to Active → reread/CRC → APPLIED.
- **Technical challenge / failure handling:** Journal records contain sequence/state/manifest fields and record CRC. Resume selects a valid matching record; interrupted Active copying requires an explicit retry after Staging recheck. A failed write does not advance accepted progress. CRC32 detects accidental corruption but does not authenticate the image.
- **Verification / limitations:** Host GCC/Clang and ASan/UBSan jobs exercise normal, corrupt and recovery paths. No MCU Flash driver, power-cut test, signatures, bootloader or device upgrade is demonstrated.
- **Reproduce:** On a Host with GCC and Python 3.10+, follow the exact [GCC compile command](https://github.com/REliasCheng/Embedded-OTA-Update-Lab/blob/0cec602fa2c1f890eb7ea8e2e98e759e5762ef6a/docs/host-update-flow.md) and run `./ota_host_demo normal`, `./ota_host_demo corrupt`, `./ota_host_demo recovery`; `python3 -m unittest discover -s tests -v` checks the independent Python range planner. No physical Flash is required.
- **Discussion points:** Why must the Journal be written before erasing Active? Why does `APPLIED` plus CRC not prove an MCU image is bootable or authentic?

## 4. STC8H8K64U — actual SDCC target image

- **Project / evidence:** [repository](https://github.com/REliasCheng/STC8-MCU-Learning) at `c517009a25e3560074f76a20274dc04956c1cdf2`; [UART1 SDCC adapter](https://github.com/REliasCheng/STC8-MCU-Learning/blob/c517009a25e3560074f76a20274dc04956c1cdf2/platform/stc8/stc8_uart_sdcc.c), [frame-drain core](https://github.com/REliasCheng/STC8-MCU-Learning/blob/c517009a25e3560074f76a20274dc04956c1cdf2/src/core/uart_frame_drain.c), [Host tests](https://github.com/REliasCheng/STC8-MCU-Learning/blob/c517009a25e3560074f76a20274dc04956c1cdf2/tests/test_uart_frame.c), [main CI](https://github.com/REliasCheng/STC8-MCU-Learning/actions/runs/40626106552), [build guide](https://github.com/REliasCheng/STC8-MCU-Learning/blob/c517009a25e3560074f76a20274dc04956c1cdf2/docs/sdcc-target-build.md).
- **Problem / implementation / architecture:** Connect a bounded UART receive pipeline to a real MCS-51 image. The repository's C89 ring buffer/frame collector and UART1 SDCC adapter are linked with a target entry. The ISR reads SBUF, clears RI and forwards one byte; foreground code drains frames with producer quiescence, keeping parsing out of the interrupt path.
- **Technical challenge / failure handling:** Ring overflow is latched and consumed so a partial frame cannot be emitted after lost bytes. The SDCC script checks the linked UART1 vector at `0x23`, Intel HEX checksums and two fresh byte-identical builds; CODE/XDATA use is reported but worst-case stack and ISR latency are not measured.
- **Verification / limitations:** CI actually compiles, links and verifies an MCS-51 HEX and runs 48 Host C89 tests. **No target instruction execution** or real board/UART/24 MHz/Keil validation is claimed.
- **Reproduce:** On Ubuntu 24.04 with distribution SDCC 4.2.0, Python 3 and no board, run `python3 scripts/build_sdcc_target.py --sdcc sdcc --output /tmp/stc8-review-1` from a fresh checkout. Run again to a *different new directory* and compare HEX files. Windows local evidence used official SDCC 4.6.4; different compiler versions need not produce identical hashes. See the build guide for exact flags and output files.
- **Discussion points:** What is the minimum bounded work in UART1 ISR versus foreground? Why does linking an ISR and checking its vector still fall short of interrupt timing or stack proof?

## 5. FreeRTOS — real Kernel on a Host Port

- **Project / evidence:** [repository](https://github.com/REliasCheng/FreeRTOS-Embedded-Lab) at `e65cec6eb5f02fd6e9e8dd2cbf416ea4586d0510`; [task pipeline](https://github.com/REliasCheng/FreeRTOS-Embedded-Lab/blob/e65cec6eb5f02fd6e9e8dd2cbf416ea4586d0510/app/rtos_demo.c), [application tests](https://github.com/REliasCheng/FreeRTOS-Embedded-Lab/blob/e65cec6eb5f02fd6e9e8dd2cbf416ea4586d0510/tests/test_processing.c), [main CI](https://github.com/REliasCheng/FreeRTOS-Embedded-Lab/actions/runs/40321931576), [runtime notes](https://github.com/REliasCheng/FreeRTOS-Embedded-Lab/blob/e65cec6eb5f02fd6e9e8dd2cbf416ea4586d0510/docs/rtos-runtime-foundation.md).
- **Problem / implementation / architecture:** Make task/IPC behavior executable instead of architecture-only. Repository-authored producer, consumer, reporter and sample-processing logic use the **official pinned FreeRTOS V11.3.2 submodule**; the Kernel is third-party. Data flows producer → four-element Queue → consumer → counted notification → reporter, with Mutex-protected shared results.
- **Technical challenge / failure handling:** Explicit scenarios exercise queue backpressure, bounded receive timeout, notification timeout and startup/lifecycle checks. Tests assert application outputs and real Kernel Queue/notification/Mutex behavior, not merely wrapper calls.
- **Verification / limitations:** Ubuntu CI builds with GCC and Clang POSIX Host Port and runs three scenarios; sanitizer jobs cover independent application logic. No Cortex-M target build, physical ISR or real-time scheduling latency is measured.
- **Reproduce:** On Linux with CMake, Ninja, GCC/Clang and POSIX development tools, run `git submodule update --init --recursive`, `cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug`, `cmake --build build --parallel`, `ctest --test-dir build --output-on-failure`, then `./build/rtos_demo normal` (also `backpressure` and `timeout`). Requires the upstream Kernel submodule, not a board.
- **Discussion points:** Which Queue semantics are truly exercised on the Host Port? Which ISR and timing conclusions require a Cortex-M port and physical measurement?

## 6. Wireless / IoT — real loopback MQTT integration

- **Project / evidence:** [repository](https://github.com/REliasCheng/Wireless-IoT-Embedded-Lab) at `b71ff86e4e9fed0fdaae6d133904c802aa80ccf3`; [portable device model](https://github.com/REliasCheng/Wireless-IoT-Embedded-Lab/blob/b71ff86e4e9fed0fdaae6d133904c802aa80ccf3/app/device_model.c), [Host MQTT adapter](https://github.com/REliasCheng/Wireless-IoT-Embedded-Lab/blob/b71ff86e4e9fed0fdaae6d133904c802aa80ccf3/app/host_mqtt_device.c), [integration tests](https://github.com/REliasCheng/Wireless-IoT-Embedded-Lab/blob/b71ff86e4e9fed0fdaae6d133904c802aa80ccf3/tests/mqtt_integration.py), [main CI](https://github.com/REliasCheng/Wireless-IoT-Embedded-Lab/actions/runs/40438227834).
- **Problem / implementation / architecture:** Separate a synthetic device model from real Host MQTT transport and recovery. The repository code validates versioned JSON commands, maintains request-ID deduplication and bounded backoff, then uses installed libmosquitto against a real loopback Broker. Independent `mosquitto_pub/sub` processes observe TCP delivery.
- **Technical challenge / failure handling:** QoS 1 can redeliver; equal request ID and value is handled idempotently while stale or conflicting commands are rejected. Tests cover disconnect/reconnect, failed subscribe/publish, silent peer and Client ID collision. Local enqueue, QoS completion and independent subscriber receipt are distinct states.
- **Verification / limitations:** GCC/Clang CI runs unit plus real Broker integration and repeats QoS 1/reconnect tests; ASan/UBSan covers model/adapter. This does not show device Wi-Fi, TLS, Aliyun, a persistent offline queue or real sensors.
- **Reproduce:** On Ubuntu 24.04 install CMake 3.20+, Ninja, `pkg-config`, GCC/Clang, Python 3, `mosquitto`, `mosquitto-clients`, `libmosquitto-dev`; run `cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug`, `cmake --build build --parallel`, `ctest --test-dir build --output-on-failure`. The tests start a loopback-only Broker; no cloud account or radio is required.
- **Discussion points:** Why does a publish call not prove subscriber delivery? What deduplication state is lost after a process restart?

## 7. ARM Linux — PTY I/O and AArch64 userspace

- **Project / evidence:** [repository](https://github.com/REliasCheng/ARM-Linux-Embedded-Lab) at `682246f2cbee1342cfc668ab027630ef18fd52e3`; [device port](https://github.com/REliasCheng/ARM-Linux-Embedded-Lab/blob/682246f2cbee1342cfc668ab027630ef18fd52e3/src/linux_device_port.c), [PTY tests](https://github.com/REliasCheng/ARM-Linux-Embedded-Lab/blob/682246f2cbee1342cfc668ab027630ef18fd52e3/tests/pty_integration.py), [main CI](https://github.com/REliasCheng/ARM-Linux-Embedded-Lab/actions/runs/40444152160), [cross-build guide](https://github.com/REliasCheng/ARM-Linux-Embedded-Lab/blob/682246f2cbee1342cfc668ab027630ef18fd52e3/docs/aarch64-build-verification.md).
- **Problem / implementation / architecture:** Build a real Linux device-I/O boundary with reproducible Host tests and an ARM64 userspace artifact. The repository's C11 port opens/configures a device fd and handles partial writes, `EINTR`, `EAGAIN` and bounded `poll`; a Python simulator creates PTYs so the monitor talks to a real Host kernel device node.
- **Technical challenge / failure handling:** Normal, malformed, disconnect and timeout scenarios check framing/recovery. AArch64 cross-build produces ELF userspace binaries; QEMU user mode executes the protocol and normal PTY scenario. A separate x86_64 external module is built against matching headers but not loaded.
- **Verification / limitations:** CI runs native GCC/Clang/sanitizer PTY tests, AArch64 cross-build plus QEMU user mode and module build. It does not boot Linux on RK3566, load a module, validate Device Tree or exercise physical UART.
- **Reproduce:** On Ubuntu 24.04 with CMake/Ninja/GCC/Python, run `cmake -S . -B build -G Ninja`, `cmake --build build --parallel`, `ctest --test-dir build --output-on-failure`. For the ARM64 tier install distribution `gcc-aarch64-linux-gnu`, `binutils-aarch64-linux-gnu`, `qemu-user`, then follow the exact [toolchain and QEMU commands](https://github.com/REliasCheng/ARM-Linux-Embedded-Lab/blob/682246f2cbee1342cfc668ab027630ef18fd52e3/docs/aarch64-build-verification.md). No board is required for these tiers.
- **Discussion points:** What does a real PTY test establish beyond a pure byte-array mock? Which assertions are impossible from a QEMU userspace run without an RK3566 kernel and board?

## 8. LVGL — host dashboard and headless rendering

- **Project / evidence:** [repository](https://github.com/REliasCheng/LVGL-Embedded-GUI-Lab) at `1bc8ab0af33b78ebc00264df885913b39802cb6d`; [UI](https://github.com/REliasCheng/LVGL-Embedded-GUI-Lab/blob/1bc8ab0af33b78ebc00264df885913b39802cb6d/app/dashboard_ui.c), [headless test](https://github.com/REliasCheng/LVGL-Embedded-GUI-Lab/blob/1bc8ab0af33b78ebc00264df885913b39802cb6d/tests/dashboard_headless.c), [main CI](https://github.com/REliasCheng/LVGL-Embedded-GUI-Lab/actions/runs/40327059878), [third-party notices](https://github.com/REliasCheng/LVGL-Embedded-GUI-Lab/blob/1bc8ab0af33b78ebc00264df885913b39802cb6d/THIRD_PARTY_NOTICES.md).
- **Problem / implementation / architecture:** Demonstrate actual GUI events and pixels with synthetic samples. Repository-authored portable model and UI build LVGL widgets/screens; an SDL2 window and a checked headless framebuffer backend supply Host display/input. LVGL v9.6.0 is a pinned upstream submodule; SDL2 is an installed system dependency.
- **Technical challenge / failure handling:** Invalid samples latch a visible FAULT without replacing the last valid sample. Recover enters PAUSED and Resume restarts sampling. Headless tests drive pointer events, run `lv_timer_handler`, inspect active widgets and compare rendered pixels, rather than checking model values alone.
- **Verification / limitations:** CI builds GCC/Clang with SDL2, runs window smoke under Xvfb and headless rendering; sanitizer jobs cover model and LVGL headless integration. No MCU LCD/touch port, DMA lifetime, FreeRTOS target task or board frame rate is demonstrated.
- **Reproduce:** On Ubuntu 24.04 install CMake 3.20+, Ninja, GCC/Clang, `libsdl2-dev`, `pkg-config`, Xvfb; initialize submodules and run `cmake -S . -B build -G Ninja -DDASHBOARD_ENABLE_SDL=ON`, `cmake --build build --parallel`, `xvfb-run -a ctest --test-dir build --output-on-failure`. The headless tier can omit SDL2. No display controller is required.
- **Discussion points:** What does pixel-difference testing catch that pure model tests miss? What new ownership and buffer-lifetime rules would an MCU display/DMA port require?
