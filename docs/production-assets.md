# SIGNALCORE production asset publication

This document began as a pre-release gate specification. Production is now active: the Profile README reads seven validated files from the independent `signalcore-assets` branch. [The production workflow](../.github/workflows/publish-assets.yml) runs on `main` pushes, a daily schedule, or manual dispatch. Its first observed `schedule` [completed successfully on 2026-10-10](https://github.com/REliasCheng/REliasCheng/actions/runs/38042558639). This record does not authorize new publication scopes or changes to repository settings.

## Initial publication gates (historical)

1. Obtain separate approval for production publication and confirm the exact approved `main` SHA, repository URL, and branch-protection policy.
2. Initialize `signalcore-assets` as an independent resource branch under a separately reviewed, normal Git operation. Do not alter `main` or rewrite any history. Preserve its first committed asset set as a recoverable version.
3. Generate both snake modes and their matching still contribution views from the same real contribution graph, plus both metrics modes and their JSON from the public API in one job. The seven files are one indivisible release set. Validate XML, the allowed SVG element/attribute/CSS subset, sizes, JSON-to-SVG equality, animated-to-still equality, fresh branch SHAs, and every required file before any commit.
4. Run `python scripts/publish_assets.py --dry-run --source <validated-directory>` and review its output. It needs only read access. Missing branch is reported as a gate, never created by the script.
5. Only after separate release approval, run the publisher's gated `--publish --approved-main-sha <exact-40-character-SHA>` path. It clones the **existing** resource branch into a temporary directory, changes only the seven validated assets, commits only if bytes changed, and performs a normal fast-forward push. A rejected push is blocked without force/rebase/retry-overwrite. If a push succeeds but the later remote read differs or fails, report `PUBLICATION_VERIFICATION_UNCERTAIN` with the pushed commit; inspect remote history before any retry. Do not call that state "no remote change."
6. Confirm all seven published asset URLs return SVG/JSON with correct MIME and payload, then switch README references in a separately reviewed normal commit. This gate has been completed: the current Profile validator checks the exact `raw.githubusercontent.com/REliasCheng/REliasCheng/signalcore-assets/` allowlist. Checked-in static fallbacks remain available. PR #1 merged the original visual Profile; later reviewed changes enabled dynamic publication.

The active production workflow uses a repository-scoped concurrency group. Its `generate` job is read-only; only the separate `publish` job has repository `contents: write`, while the publisher script targets the resource branch and verifies the current `main` SHA and CI state before a normal fast-forward publication. The old Snake and Metrics preview workflows upload artifacts only and no longer have daily schedules; their manual and preview-branch triggers remain. Do not use `pull_request_target` to execute untrusted PR code with write credentials. Protecting `main` must not accidentally block publication to `signalcore-assets`.

`refreshed_utc` is the UTC public-API collection timestamp; the SVG displays that same timestamp. A dated checked-in snapshot may remain visible with its historical label after failures, but dry-run publication and `--publish` reject source older than 48 hours or more than five minutes in the future. Remote `main` SHAs and CI states are rechecked immediately before publishing. Publication time is the asset-branch commit time, distinct from collection time. A failed API request must not advance either timestamp or replace the last valid asset set.

## Failure behavior

An API timeout, error page, empty inventory, missing dark/light or still file, invalid or oversized SVG, stale metrics timestamp/CI SHA, unexpected remote, absent resource branch, or concurrent non-fast-forward stops the publication before an accepted push. A post-push verification failure is explicitly uncertain: the branch may already have changed and must be inspected. A failed run must not refresh the displayed date or claim `PASS`. A normal forward/revert commit can restore a previous good set after reviewing its contents; do not force-push.

The dated metrics panel reports public repository count, primary language **by repository**, and five host-CI workflows matched to their respective current `main` SHA. It is not real-time telemetry, a language-byte ratio, a hardware-validation result, or an engineering-quality score. The contribution animation is generated from the public graph, not invented activity. Keep static fallbacks permanently. The README offers static contribution sources for reduced-motion users; automatic selection in a real reduced-motion browser remains to be verified.
